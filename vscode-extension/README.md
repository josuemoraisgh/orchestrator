# Orchestrator-AI VS Code extension

This extension contributes a reusable **Orquestrador** agent to the VS Code Chat agent picker and tools for initializing project guidance, installing/checking the managed AI Memory runtime and Lich compatibility adapter, delegating bounded work, synchronizing configured upstream repositories, and building a project.

The extension is project-neutral. Each project owns its requirements in `.ai/specs/`, and receives generic procedures in `.ai/skills/`. On activation, it opens an Orquestrador view in the Secondary Side Bar with its own conversation list and message composer. The coordinator can use a VS Code language model or a read-only Claude/Codex CLI profile. Worker tasks use Orchestrator-owned VS Code model, Codex app-server, or Claude Code CLI adapters where available; other compatible CLIs can use the transitional Lich executor. Task continuity is stored locally and in verified AI Memory pages when available. Settings open from the gear in the Chat or Orquestrador view title.

## Project configuration

The Lich cost row is a project aggregate. If its initial lookup runs before the automatic tool installation finishes, the view retries when installation completes; it does not report per-account usage or plan quotas.

The **Configurações** dialog exposes the build executable, arguments, working directory, timeout, upstream repositories, optional tool command overrides, allowed worker providers, and the task parallelism limit shared across plans and VS Code windows using the same user profile. A lock-protected ledger in the extension global storage reserves each task before dispatch, prevents duplicate dispatch. Lich session leases are reconciled against `lich sessions --json` only when a task uses the Lich compatibility executor. The same inventory read supplies both reconciliation and the reservation baseline, avoiding a second fallible check between verification and dispatch. If Lich state cannot be checked, leases are retained and scheduling reports that it is waiting, avoiding an unverifiable concurrency count. When a Lich task is scheduled, visible untracked Lich sessions in the same project also occupy parallel slots: busy, waiting, and unknown states count conservatively, while done is free. VS Code profiles for the same OS user share the task reservation ledger; separate OS user accounts have independent ledgers. Its provider list detects installed agent CLIs and model providers registered through VS Code, rather than listing every task-specific agent profile contributed by extensions. It discovers models exposed by the selected VS Code provider. The Orchestrator chat can use that public model API or a Claude/Codex CLI coordinator profile; it never reads another extension's private credentials. The worker defaults select a detected provider CLI, model, and effort. For Claude and Codex, settings can open the CLI's official login flow and run its documented authentication status command; other CLIs remain unverified unless the provider exposes a supported status interface. The extension displays only the verification result and does not read or store credentials. The Orquestrador chat also displays Lich's known project cost for the last 30 days when `lich cost --json` provides it, including sessions Lich could not price. That report is project-aggregated; it does not identify account profiles, plan quotas, or usage unavailable from Lich.

The settings dialog also controls the maximum attempts per task (1?5, including the first run) and an optional estimated USD budget per plan. When enabled, every task must include a user-reviewable one-attempt estimate. The scheduler atomically reserves estimates across VS Code windows sharing the same user profile; retries and handoffs reserve another attempt, and dispatch pauses when the configured ceiling would be exceeded. Reservations remain counted even if an attempt fails or is cancelled. These are planning estimates, not provider quotes, actual charges, or quota measurements; Lich cost data remains project-wide and cannot be reliably attributed to a task or account.

For the VS Code Language Model API path, effort is not set because VS Code publishes no generic reasoning-effort option. Claude and Codex CLI coordinators accept a model and effort setting. A task can override its executor, provider, model, effort, authorized CLI profile, and worktree base in the reviewed plan. Provider worker sessions can be stopped and parked with their checkout preserved. Continuing in a different provider starts a new session in that same checkout and needs a concise handoff; conversation history is not migrated between providers. The first-party Claude adapter can continue its provider session and apply the selected model/effort for the new task when supported by the official CLI.

The **Preparar projeto (.ai)** button is enabled only when the workspace has no `.ai` path. It creates `.ai/specs`, `.ai/skills`, the bundled generic skills, and initial settings. If `.ai` already exists, the button is disabled and initialization makes no changes.

The command **Orchestrator: Open Configured Agent in New Chat Session** opens the configured agent in native VS Code Chat when needed.

The Orquestrador tab can call the selected VS Code language model through the public Language Model API or a selected Claude/Codex CLI profile. CLI coordinator requests run with project read access only, no edit tools, and no enabled MCP tools; the extension supplies a bounded AI Memory briefing plus verified page excerpts for active board tasks when its read tools are available; those pages are labeled as untrusted history. The tab then requires an editable, persisted task plan to be approved before starting any worker sessions. The task board stores dependencies, provider/model/effort, worktree/base branch, provider session/ticket, results, retry history, and review state in VS Code workspace state. Independent tasks run in Orchestrator-managed isolated Git worktrees when the project is a Git checkout; without Git, dispatch is serial. A plan may set `worktree` to `current` for a task that explicitly needs the open checkout's uncommitted files; this runs in the project checkout and shares local changes, with the plan approval serving as the confirmation. Leave it empty for the default isolated worktree. Set `base` to a listed local branch to select its commit; otherwise the worktree starts from `HEAD`. A project `.worktreeinclude` copies only explicitly matched Git-ignored files into new worktrees, never overwriting existing files. Before starting a Lich compatibility task, the extension checks Lich's live session list and worktree list and refuses a checkout already occupied by another session. For Lich compatibility tasks, if the project is not open yet, it verifies that the generated branch does not already exist before `lich open --project` opens the project on first use. A completed Orchestrator session is parked before a later approved task reuses that same checkout. While a Lich ticket is pending, the board periodically records changed paths from that task's Git worktree and writes a task-memory update when the file set changes. When the ticket returns a result, the board captures a bounded preview of tracked-file diffs; new files remain listed separately. Each task also shows the last 20 observed events, including Lich state changes, changed-file snapshots, handoffs, and results. Lich 0.85 exposes session state through `sessions --json` and final ticket responses through `wait`; it does not expose a generic live transcript stream, so the timeline is not a transcript of the agent's reasoning or intermediate output. The coordinator leaves completion pending until a person reviews the acceptance criteria. Pause stops active provider sessions and preserves their checkouts; resume continues the same provider conversation where its official adapter supports it, otherwise it starts a replacement with a handoff. Cancellation also stops sessions and preserves their checkouts. On view activation after an extension-host reload, saved tickets are reconciled and dispatch resumes for approved, unpaused plans; intentionally paused plans stay paused.

Orchestrator runs the official, pinned AI Memory executable as a private loopback service in its own VS Code global storage. It initializes a dedicated data directory and accesses the service through AI Memory's official MCP bridge. Orchestrator does not install Codex lifecycle hooks or change Codex configuration: those hooks are only needed to capture direct Codex-session events, not for Orchestrator's task-scoped memory reads and writes. This avoids an unexpected Codex hook-review prompt; provider configuration remains untouched. Task and attempt pages are stored in that private AI Memory database. Every read/write names the configured workspace and project. New projects can be created by AI Memory's documented `memory_write_page` behavior; reads and writes are verified before a task is dispatched. Before opening a supported worker, the coordinator reads the task page and latest attempt reports and places a bounded excerpt into the worker context as untrusted historical evidence. Workers receive the scope and page paths and are instructed to read and update the report with page-ID compare-and-set and read-back verification. If the worker cannot update the report, Orchestrator may store a coordinator-authored fallback based on the verified worker result and observed checkout. Missing or failed page operations remain unverified.

Tasks with an unverified AI Memory state expose **Sincronizar memória** in the Orquestrador panel. This retries the coordinator's task-page write and read-back, and retries verification of the agent report when one exists; the UI only reports memory as confirmed after successful verification.

These pages are supported shared project wiki pages, not private per-agent namespaces and not AI Memory managed workstreams. Claude Code and Codex use first-party provider-session adapters; other compatible CLIs may use the Lich adapter; it does not establish AI Memory's native managed-workstream/session links, which are created through `ai-memory run`. Cross-provider continuation is therefore only confirmed when the receiving provider's actual read/write succeeds. The worker must report the real result of its AI Memory operations; passing paths in a prompt alone is not proof of access. Retrieved pages and previous-agent handoffs are treated as untrusted historical evidence, not executable instructions.

### Coordinator profiles

In Configurações, select Claude or Codex as the coordinator, add a named profile, choose its model and effort, and use **Login oficial** to authenticate through that CLI. An existing-login profile reuses the CLI's current login. Claude can use a separate `CLAUDE_CONFIG_DIR`; the extension confirms the path reported by `claude auth status --json` before using it. Profile metadata stays in the VS Code extension's global storage, while authentication remains managed by the provider CLI. No token is read by the extension.

Isolated Codex profiles use separate `CODEX_HOME` directories and set the documented `cli_auth_credentials_store = "file"`, which stores credentials in that profile's CLI-managed `auth.json` rather than the shared system keyring. The extension starts the official Codex login in that profile and never reads the credential file; Codex file storage is not encrypted by the Orchestrator. It also does not select multiple Copilot/Gemini identities through the VS Code model API.

These profiles can select the Orchestrator chat coordinator and be assigned to Claude/Codex worker tasks in the reviewed plan. The Lich compatibility launcher does not expose a per-task account selector. The current pinned Lich release supports multiple Claude and Codex account profiles in its Providers UI and lets a person move a session between accounts in the same card. Its documented `lich open` command and `open_session` MCP tool do not accept a profile/account field, so this extension cannot choose or verify a worker profile programmatically; use Lich's own UI for that operation. Cost reporting remains project-aggregated and cannot report per-profile quota or usage.

### Provider and authentication compatibility

The repository referenced as ?LICH Lite? is currently named **lich**. It is a terminal-first agent desktop/CLI, not a VS Code extension or embeddable chat UI. Its CLI can open multiple provider sessions and worktrees; its public contract states that it does not read agent terminal output. It sends work through the provider CLI and can collect a response when the agent uses the Lich reply mechanism. Current provider docs mark the `control` prompt/model/effort interface as available for Claude Code only; other providers require closing/parking and starting a new session to switch.

| Provider path | Orchestrator chat | Worker executor | Authentication state |
| --- | --- | --- | --- |
| VS Code Language Model API | Supported when the model is exposed by `vscode.lm` | First-party model worker | Model is discovered; first request may require VS Code consent/access. No credentials are read by this extension. |
| Claude/Codex CLI | Supported for the coordinator through restricted/read-only planning commands | First-party Claude and Codex adapters; Lich fallback for other CLIs | Coordinator profile readiness is checked with the documented CLI status command. The worker CLI uses its own official login and the extension cannot borrow a chat extension's private session. |
| Provider extension without a published model/CLI interface | Not supported | Not supported | Shown as unavailable rather than authenticated. |

VS Code's supported cross-extension authentication API is `vscode.authentication`, which is consent-based and requires a provider ID and scopes. VS Code does not provide a public way to enumerate another extension's private sessions or pass them to a separate CLI. The Codex and Claude chat extensions do not publish a compatible Orchestrator/Lich session bridge in the interfaces this extension uses. Therefore no cross-extension credential reuse is claimed. Use the provider's documented CLI sign-in when Orchestrator reports that the CLI is unauthenticated. Provider readiness remains unverified until an actual model request or CLI task succeeds.

Lich's current repository is AGPL-3.0-only (releases through v0.9.0 were MIT); this extension downloads its official binary release and does not copy its UI or source. ai-memory is MIT and is integrated through its installed CLI/MCP support. Native Windows support in ai-memory is currently experimental.

Declare source repositories and build details in the Configurações dialog, opened from the Chat gear. The extension performs fetch plus fast-forward-only merge and refuses dirty repositories. `#syncAndBuildProject` performs this synchronization before invoking the configured build.

## Tools

- `#initializeProjectGuidance` creates `.ai/specs`, `.ai/skills`, and a starter configuration without overwriting files.
- `#checkOrchestratorTools` checks the local `lich` and `ai-memory` commands.
- `#listLichSessions` lists live sessions.
- The native `@Orquestrador` profile cannot start or transfer Lich work outside the persistent plan review in the Orquestrador tab.
- `#stopLichTask` stops and parks an active Lich session without deleting its checkout.
- Lich tasks are resumed and handed off from the Orquestrador task board, where the approved plan and task memory remain attached.
- `#syncProjectUpstreams` fast-forward updates only configured upstreams, with confirmation.
- `#syncAndBuildProject` syncs first and then runs the configured build, with confirmation.

On first use, the extension downloads the pinned official Windows x64 release assets, verifies their SHA-256 digests, and installs them under Orchestrator's VS Code global storage. AI Memory runs as a private managed service. The package carries the AI Memory and `ignore` MIT notices in `THIRD-PARTY-NOTICES.md`; their sources remain available from their upstream projects.

For each release package, `npm run package` checks the latest stable GitHub releases and pins their tags, asset URLs, and hashes in `upstream-releases.json`. The extension then installs exactly the versions recorded in that package; the next extension release can pick up newer upstream versions. This gives each published VSIX a reproducible dependency set.

## Platform and licensing notes

The automatic installer currently supports Windows x64. The current AI Memory support matrix marks native Windows experimental; Linux/macOS installers and validation still need to be added before claiming cross-platform support. Lich's current releases use AGPL-3.0-only, so the extension fetches its official release at install time instead of redistributing the binary.

The Chat agent uses VS Code's current custom-agent contribution rather than the deprecated chat participant API. The Python implementation is being retired in favor of this extension workflow.
